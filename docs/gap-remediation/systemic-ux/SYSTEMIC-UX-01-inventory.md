## Contracts derived from the implementations

1. **Control/output co-visibility.** Group the current image/model and its real control inside
   the renderer that owns both. At 1600×900, 1440×900 and 1024×768, test their full bounding boxes
   against the usable viewport after ordinary access to the workbench. Entry must expose the
   visual or a recognizable portion. Compact layouts may stack, but no unrelated prose or
   navigation belongs between a control and its output. Graphical viewports may be bounded;
   teaching text and the document must remain content-sized and scrollable.
2. **Truthful availability.** A control is operable, natively disabled with a truthful reason,
   or visibly illustrative. Inherited fieldset disabled state counts. Styling must not imply
   that a locked response is still an open answer. Preserve safety, media-readiness, pending
   confirmation and source-dependent restrictions rather than inventing an action.
3. **Visual discoverability.** Put the current exercise before unrelated/supporting material.
   Keep all authored material and its meaning. Do not mark a visual viewed, start playback,
   acquire an image, or advance the engine merely because a component mounted or resized.
4. **Primary action clarity.** One emphasized current action; secondary skip/explain/retry remain
   available. No new answer, correctness or competence gate. Preserve each module's persistence
   contract and actual source of progression. A visual readiness condition is not mastery.
5. **Progressive workbench.** Reuse the same real image/control renderer across related steps;
   layout must not reset, replay or re-author the task. A shared mental model does not authorize
   merging clinical lessons. Record consolidation candidates in the separate content review.

The batch uses module-local adapters because the defects have different owners (R3F suite,
recorded-video iframe, scope bench, canonical circuit). Shared `StageLayout` is not the common
cause. No viewport-fixed teaching overlay, scroll-jacking, new automatic focus move or new
progress store is needed.

## Consolidated discovery after the initial inventory

The first edit began only after the inventory above was recorded. Browser regression then
identified a related CRRT scroll-owner defect and the audit continued: on the baseline production
build at 1440×900, the introductory lesson rendered in document flow while the inherited
`data-critical-care-activity-shell` selector set `body` and `#main-content` to `overflow: hidden`.
A native 350px wheel gesture left `scrollY` at 0. Programmatic focus scrolling had obscured this
failure in the initial measurements. This is an adapter mismatch, not a reason to change every
StageLayout. A provisional local CRRT override established the correct scroll owner, then was
replaced by the shared declaration described below when the same defect was reproduced in two
other modules. Paired-visibility browser tests now use native wheel scrolling, followed by
keyboard manipulation with no scroll between change and observation.

The final layout and measured outcomes are recorded in the handoff. Baseline entries remain
historical observations; they are not silently rewritten as post-change passes.

The subsequent nine-module native-wheel audit also reproduced the ancestor lock in MV
(`ventilation-and-co2`, document height 2621px, no task scroll owner) and MCS
(`iabp-timing-triggering`, document height 2204px, only a closed source-list scroller).
Both left `scrollY` at 0 after a 350px wheel gesture. This establishes a genuinely shared
infrastructure defect: the global workspace lock did not distinguish explicit document-flow
adapters. The final repair therefore replaces the provisional CRRT-only CSS override with a
shared `data-learning-document-flow` opt-out declared by the existing CRRT focused-lesson,
MV task-flow and MCS flowing adapters. The lock still applies to actual viewport workspaces.
BBT and ECMO each keep the document at one viewport with a real internal task scroll owner;
they must not inherit the document-flow opt-out. BF, PI, EBUS and HD already scroll the page.

Production verification also exposed two local consequences at 1024×768. CRRT's now-unlocked
document allowed the old lesson heading to stick, leaving the paired circuit bottom at y821
outside the 768px viewport. The foundation heading now stays in normal flow at every width.
PI's comparison dock placed the range under the course header when a rapid Shift+Tab / Tab
sequence interrupted native smooth scrolling. Existing measured focus padding was correct;
the local document now uses immediate native scrolling, retaining the PI focus/outline hooks
and without adding scripted scrolling or focus movement. Both repairs preserve the current
instruction, all controls and teaching. They are engineering layout fixes, not curriculum changes.

Final screenshot inspection found another CRRT consequence: self-paced Continue from a long
reading preserved the previous document offset, opening the next task with its heading above
the viewport (particularly at phone widths). The existing completed-exercise path also scrolled
before React replaced the task. `CrrtFoundationLesson` now reveals the current task after a
user-directed task-location change commits. It skips initial mounting and ordinary control
operations, and does not move focus. The browser matrix checks that the new heading is
uncovered as well as checking control/output geometry. This is the local continuation owner,
not a new completion gate or shared-stage behavior.

# R0 — freeze and contract inventory

Every mechanism on `main` that currently constrains the ECMO Learn flow, with a disposition.
The rule this document exists to enforce: **no freeze contract is removed without a named
replacement.** A failing freeze test is a signal to decide what should be pinned instead, never
a licence to delete the pin.

Context worth stating once: the twenty-eight-file SHA-256 byte-freeze contract lives only on the
held branch of draft PR #94. `main` has no byte-hash test. On `main` the freeze is enforced by
registry, count, and copy pins plus the B5 instrument guards — and, notably, **no test on `main`
asserts the hub's call-to-action target, its counts, or its copy**; `CardiohelpHub.tsx` has no
component test at all. That gap is what let the entry conflict persist, and R1 closes it.

Dispositions: **retain** (unchanged) · **re-scope** (kept, meaning clarified) · **narrow**
(assertion tightened to a new invariant) · **extend** (kept plus new cases) · **superseded**
(replaced by a named contract).

| Artifact                                                                                                                                                               | What it pins                                 | Disposition                             | Replacement / rationale                                                                                                                                                                                                                                                                                                                              |

| `EcmoFoundationLessonActivity.tsx` header contract comment                                                                                                             | the authored stance                          | **Replace wording**                     | Rewritten to state precisely what is now true: a traversal marker is recorded on transfer commit; no scenario result, mastery, score, or Practice progress is ever written.                                                                                                                                                                          |

**Guard-evasion hazard, recorded deliberately.** The current guards detect persistence by
scanning the component's source for literal strings (`writeProgress`, `localStorage`,
`ProgressV2`, `from '…progress'`) and by spying on `Storage.prototype` at mount only. A writer
imported through the `'../engine'` barrel and fired on click would satisfy every one of those
checks while gutting their intent. The narrowed guards therefore assert _observed storage
behaviour_ around the real interaction, not source text alone. Anyone later relaxing these
tests should read this paragraph first.
